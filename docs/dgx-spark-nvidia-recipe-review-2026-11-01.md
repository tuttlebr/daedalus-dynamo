# DGX Spark recipe review — 2026-11-01

Historical baseline: the findings below describe the values before implementation.
See [NVIDIA Spark recipes](nvidia-spark-recipes.md) for the subsequent code changes;
those changes have not been deployed or GPU-qualified.

The 40 DGX Spark recipes in `values/` are **not a reproduction of NVIDIA's published recommendations**. They are primarily conservative, generated Dynamo candidates. Ten have an exact checkpoint match in NVIDIA's single-Spark vLLM recipes, and all ten have material configuration differences. One uses a different Flash Next checkpoint. The remaining 29 have no matching single-Spark recipe in the supplied catalog; that is a coverage gap, not evidence that those models are unsupported.

This review made no changes to values, images, deployments, routes, ports, authentication, or running services. It does not certify GPU execution or performance. The deliverables are this review and its local evidence files.

Source: [NVIDIA local-ai-inference-recipes](https://github.com/NVIDIA/local-ai-inference-recipes/tree/7b2ee453234617f58e1e100c195ac3be7f79e233), commit `7b2ee453234617f58e1e100c195ac3be7f79e233` (release v0.66, 2026-10-24), retrieved 2026-11-01. Compared actual `recipe.yaml` files, not just website labels. Local baseline: `b47d3e6110a60ea884a0dd56665798432a7ac950`. Exact checkpoint, Linux, vLLM, one GPU and one node were required. Where both 64 GB and 128 GB variants exist, the 128 GB variant was selected. Lightning only has a single-Spark recipe with a 64 GB minimum; it is included as a capacity-compatible reference, explicitly not a separate 128 GB benchmark.

**Findings requiring attention**

1. **Qwen3.8-27B cannot reproduce the 128 GB recommendation with the current shared image.** Its local values inherit memory utilization `0.90`, Marlin and eager execution. NVIDIA specifies `0.60`, a patched NGC runtime, dynamic NVFP4 kernel configuration, CUDA-graph compilation and seven-token DFlash2 speculation. NVIDIA reports startup hangs at higher memory settings and a prefix-cache correctness dependency. Inspection of the running ARM64 `vllm-runtime:1.6.1` image found vLLM `0.31.0`, but its kernel configuration lacks `nvfp4_dynamic`, `nvfp4_dynamic_max_tokens` and `unquantized_linear_backend`. A matching version number alone is insufficient. This is not evidence that your current non-speculative recipe produces corrupted text; the upstream correctness warning concerns DFlash2. [NVIDIA source](https://github.com/NVIDIA/local-ai-inference-recipes/blob/7b2ee453234617f58e1e100c195ac3be7f79e233/models/qwen/qwen3.8-27b/dgx-spark/linux/vllm/128gb/nvfp4/recipe.yaml).

2. **The generic Spark memory allocation is too aggressive to treat as a safe universal default.** Thirty-nine recipes inherit `gpu-memory-utilization: 0.90`; Muse alone uses `0.70`. The machine has approximately 121.6 GiB total host RAM, shared with its GPU. The read-only host snapshot showed approximately 95 GiB available, while a 0.90 allocation is approximately 109 GiB before accounting for additional CPU allocations. Availability changes, and Linux `MemAvailable` is not a CUDA free-memory measurement, but this is a concrete headroom concern. The earlier Muse evidence already records a 0.90 startup failure with 99.31 GiB free. NVIDIA's matching recipes use 0.80, except Qwen3.6-27B at 0.50 and Qwen3.8-27B at 0.60. Do not lower every model to the same fraction: larger weights may then fail to fit. [Spark defaults](../values/_hardware/dgx-spark.yaml), [local memory evidence](../artifacts/nvidia-spark-review-20261101/live-inventory.json), [earlier Muse evidence](model-recipes.md).

3. **The ten matched recipes do not configure NVIDIA's chat/tool/reasoning parsers on the Dynamo frontend.** All ten resolve to an empty `frontend.extraArgs`. NVIDIA's monolithic `vllm serve` flags must be mapped to the component that processes chat. In this chart that means configuring the separate frontend, as the existing Muse tuning already does with `--dyn-chat-processor vllm`. Merely adding tool-parser flags to the worker does not establish correct frontend behavior. Test structured tool calls and reasoning separation, including streaming, rather than relying on a successful `/v1/models` response. [Existing frontend example](../values/meta/muse-glimmer-30b-nvfp4/_tuning.yaml), [frontend launch template](../charts/dynamo-model/templates/dgd.yaml).

4. **Generic candidate settings omit model-specific execution requirements.** DiffusionGemma is missing its diffusion configuration. Nemotron Super is missing the recommended Mamba/cache/environment settings. All ten matched recipes omit the published speculative configuration where one is present. These omissions range from behavioral prerequisites to performance choices; they are not all launch failures. Details below identify each model's expected settings.

5. **Flash Next is a different deployment recipe, not just different flags.** The local checkpoint is `nvidia/Qwen3.8-Flash-Next-NVFP4`, with a custom mmap/NVMe runtime. NVIDIA's one-Spark reference uses `nvidia/Qwen3.8-Flash-Next-FP4-Local`, a B12x image, `modelopt_mixed`, the B12x loader/kernels and a different disk-offload environment. Do not switch the model ID while retaining the current revision, cache or custom patches. A migration needs its own pinned checkpoint, cache and runtime qualification. [NVIDIA source](https://github.com/NVIDIA/local-ai-inference-recipes/blob/7b2ee453234617f58e1e100c195ac3be7f79e233/models/qwen/qwen3.8-flash-next/dgx-spark/linux/vllm/fp4-local/recipe.yaml).

6. **Offline fit results and current pod requests do not certify runtime memory.** The generator screens mostly at 8,192 tokens, one sequence and an assumed KV layout; runtime context is `auto`. Most Spark pod requests account for estimated weights plus that screening workload, not the full memory fraction vLLM is permitted to consume. In shared CPU/GPU RAM, this can let Kubernetes admit other CPU workloads despite substantial GPU-side consumption. Scout FP8 has 103.924 GiB of checkpoint files and a 108.924 GiB screening estimate, exceeding the observed available host memory. Mistral Medium's 95.435 GiB estimate leaves almost no headroom in that snapshot. These candidates need a fresh fit and startup measurement; file sizes are not an exact runtime allocation. [Fit calculations](../scripts/build_model_catalog.py), [recorded assessments](../config/model-catalog/recipes.json).

**What is already correct**

All 40 select `NVIDIA-GB10` and `arm64`, request one GPU, use TP1/PP1/DP1 and one worker replica, and disable Planner and worker autoscaling. Model revisions are pinned. The shared launch stays within the existing Dynamo topology. Those are appropriate foundations for one Spark.

The current repository intentionally selects automatic context, concurrency one, eager execution and generally BF16 KV (`dtype: bfloat16`, `kv-cache-dtype: auto`). These can be valid local tradeoffs. They do not reproduce NVIDIA's optimized measurements, and automatic context does not promise the same 262,144-token window or the same memory/concurrency behavior. The latest local context-policy commit is `fe2b650` (`use auto max token len`); changing that policy is a separate decision from fixing missing model requirements.
